# AI4SE 期末项目反思

完成 Coding Agent Harness 之后，我最大的变化，是不再把“让模型生成代码”理解成 AI 软件工程的核心。真正困难的部分，是如何把一个概率性的决策器放进由确定性机制组成的系统：它能做什么、什么时候必须停下、失败后得到什么反馈、上下文如何组织，以及我凭什么相信它已经完成。这些问题最后都落到了 harness，而不是 prompt 上。

## 哪些 Superpowers 技能真正发挥了作用

对我帮助最大的是 brainstorming、test-driven-development、subagent-driven-development 和 requesting-code-review。Brainstorming 的价值并不是替我想出功能，而是持续逼我明确边界。项目最后选择把反馈闭环作为主要贡献，就是因为讨论过程中逐渐确认：六个维度都做完整只能证明“像一个 harness”，必须再选一个能用代码深入验证的维度，项目才有工程重点。

冷启动验证是我认为最有价值的一步。我让一个没有对话历史的 Codex 只读取 SPEC 和 PLAN，并要求遇到不确定之处就暂停。它在 Task 1 甚至还没有开始写产品代码，就发现计划要求先运行 `make test`，但 Makefile 和依赖要到后续步骤才创建。这个问题我和主 agent 都没有察觉，因为我们共享了太多隐性上下文。后来我把顺序改为 bootstrap、失败测试、RED、GREEN，第二轮才真正跑出 `ModuleNotFoundError` 并完成最小实现。这个案例说明，spec 是否清楚不能由作者自己证明，必须让陌生执行者尝试使用。

相对而言，部分技能也有形式化过重的问题。Writing-plans 要求把每一步写到文件、命令和预期输出，最终 PLAN 很长，人类很难一次通读。但它的好处是 subagent 不必自行补全接口，Task 2 的数据模型一旦确定，后续工具、事件、反馈和审批模块就能独立推进。我的结论不是删掉详细计划，而是把它分成“人类可读的任务总表”和“agent 可执行的逐步 brief”两层。

## TDD 是阻碍还是放大器

在这个项目里，TDD 总体上是放大器。对于 Redactor、guardrail、classifier 和状态机，它把“应该安全”“应该能恢复”变成了可以重复执行的断言。尤其是 CorrectionLoop，初版虽然通过 happy-path 测试，但最终评审指出预算耗尽、重复失败和 LLM 无动作三个停机分支没有覆盖。补齐这些测试后，我才有资格说反馈闭环的停止条件是完整的。

TDD 也暴露了一个容易被忽略的问题：测试通过不等于测试到了目标分支。Task 13 中，一个名为“approval approved”的测试使用 `echo ok`，实际上没有匹配审批规则，直接走了 Allow 分支。评审者建议换成 `pip install`，但那会引入网络和环境副作用。我最终增加无副作用的 `approve-me` 标记，让命令稳定进入 RequireApproval，再由脚本式 gateway 批准。这个修正让我认识到，测试名称和绿色结果都只是表面证据，关键是沿控制流确认输入真正经过了目标机制。

TDD 产生阻力的地方主要是跨环境命令。Windows 宿主、Linux 容器和 GitHub Actions 对 PATH、编码和文件权限的行为不同。如果测试把某个宿主的偶然行为写成产品语义，就会得到脆弱的绿色。因此我逐渐把测试分成三类：纯函数和状态机在任意宿主上确定性运行；工具解析测试验证结构化机制；真实命令链和镜像行为交给 Linux 容器与 CI。

## Subagent 工作流与任务颗粒度

Subagent 在边界清楚时可以持续完成一个模块，但不适合一次承担整个系统。最合适的颗粒度不是机械的“2–5 分钟”，而是一个能够独立 RED、GREEN、评审和提交的行为单元。例如 ClockPort、Redactor、classifier 都很适合单 task；CorrectionLoop 则必须包含完整状态转换，继续拆小会让每个 subagent 都缺少状态机全貌。

我采用新鲜 subagent 实现单一任务，再做 spec 合规和代码质量两阶段评审。这个模式最明显的收益是问题不会被“实现者自己解释掉”。Task 7 的实现者认为 `clear()` 捕获所有异常可以保持幂等，但 reviewer 指出这会掩盖权限和后端故障。我选择只捕获 `PasswordDeleteError`，修复后再评审。人工价值并不是亲自重写全部代码，而是在两个合理目标冲突时决定系统应保留哪一个性质。

## Prompt 与 Context 策略

最有效的策略是给 subagent 一个封闭任务包：精确文件路径、上游接口、需要先看到的失败、禁止扩展的范围和验收命令。对实现 agent，我尽量不给整段历史对话，避免它依赖隐性背景；对 reviewer，则提供 commit 区间、任务 brief 和需要分别检查的 spec/quality 维度。MockLLM、FrozenClock、ScriptedApprovalGateway 也是 context engineering 的一部分：它们不是文字提示，而是把不确定环境替换成可控制输入。

## 凭据与分发带来的工程思考

凭据要求迫使我把秘密经过的每一条路径画出来：输入、存储、ToolResult、EventLog、终端和镜像。仅仅“不把 key 写进代码”是不够的，工具 stdout 和 stderr 同样可能把 key 带回上下文。因此 Redactor 被放在结果边界，并用纯函数测试验证；查看状态只显示尾四位；仓库和提交前再做密钥形状扫描。这个过程让我意识到，安全不是一个模块，而是一组跨边界的不变量。

Docker 和 CI 则让我看到“本地通过”有多不可靠。镜像第一次能构建，但缺少 `PYTHONPATH`；修复后，非 root 用户又不能写 `/app`；随后产品镜像因为不包含 `.github/`，仓库上下文测试再次失败。三次故障分别属于入口、权限和测试作用域，只有真正执行镜像内测试才能区分。分发要求最终迫使我验证的是别人得到的产物，而不是我的开发目录。

## 如果重做，我会改变什么

如果重做，我会更早建立三层验证矩阵：宿主单元测试、容器集成测试、远端 CI，并在 PLAN 中明确每个测试属于哪一层。我也会在每个 task 完成时同步更新 PLAN 和 AGENT_LOG，而不是最后从 commit 和 report 回填。对于主要贡献，我会在设计阶段就列出完整状态转移表和每个停机分支的测试，避免 happy path 先通过后再补关键覆盖。

我对 Superpowers 的最终评价是：它擅长守住纪律，但不能保证判断正确。它假设任务可以被清晰拆分、测试能够代表需求、reviewer 能发现实现者的盲点。这些假设在本项目中大体成立，却都有边界。计划可能自身不可执行，绿色测试可能没有进入目标分支，review 建议也可能引入真实网络副作用。工程师仍然必须阅读证据、理解控制流、区分环境，并对偏离作出可解释的决定。Superpowers 提供的是约束判断过程的脚手架，而不是替代判断的人。
